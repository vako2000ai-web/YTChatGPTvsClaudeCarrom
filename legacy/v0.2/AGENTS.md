# Carrom AI Showdown — инструкции для разработки

## Назначение и статус

Python/Pygame/Pymunk игра: OpenAI против Anthropic через API. Игра должна
проводить матч без ручного запуска каждого удара. Текущая версия 0.2.0 —
автоматический прототип с явно обозначенными домашними правилами, не финальный
турнирный Carrom. Дорожная карта находится в PROJECT_PLAN.md.

## Как работать

- Сначала прочитать README.md и PROJECT_PLAN.md, затем код соответствующего модуля.
- Сохранять существующие файлы, не удалять пользовательские данные и журналы.
- `legacy/v0.1/` — исходники из исходного архива, не менять при разработке 0.2.
- Не выполнять массовый рефакторинг без конкретной причины; изменения делать небольшими.
- Тексты документации, комментарии в эфире и отчёты для пользователя — на русском.
- Обновлять версию, документацию и план при изменении правил или формата состояния.
- Не утверждать, что полные правила, Windows exe или запись видео готовы без проверок.

## Архитектура

- board.py: единственный источник геометрии и физических параметров.
- engine.py: Pymunk, фиксированный DT, размещение, лузы и возврат фишек.
- rules.py: правила, без Pygame/API; состояние меняется один раз на ход.
- agents.py: одинаковый контракт решения, API-адаптеры и отдельная demo-стратегия.
- settings.py: чтение конфигурации из .env рядом с исходниками/исполняемым файлом.
- runner.py: жизненный цикл матча, фоновые запросы, JSONL.
- game.py: интерфейс и CLI, запуск серий и экспорт JSON/CSV.
- tests/: unit, integration и SDL dummy smoke.

## Инварианты

- Только главный поток меняет Pygame/Pymunk и правила.
- API worker получает сериализуемый снимок, не ссылки на физические объекты.
- На каждый запрос приходится не больше одного результата и одного завершения хода.
- После завершения удара все скорости обнулены, страйкер удалён.
- 19 исходных ID всегда находятся на доске, в банке, в текущих лузах или в состоянии королевы.
- Позиции возврата не пересекаются с существующими фишками.
- Неверный ответ/сбой API учитывается как пропуск хода и не блокирует автоматический матч.
- Обе модели получают один формат состояния, одинаковую геометрию, правила и ограничения.
- В режиме api никогда не подменять решения локальной стратегией.
- Demo в интерфейсе и журнале должен быть явно помечен как локальная стратегия.

## Секреты и расходы

- Ключи хранить только в .env. Не выводить файл, ключи, HTTP headers и SDK exceptions в лог.
- .env и его варианты игнорируются Git; .env.example содержит только пустые поля ключей.
- Не включать .env в архивы, Windows-сборку, CI artifacts и видео.
- Нет ключей/ID моделей — понятная ошибка до начала API-матча.
- Реальные оплачиваемые запросы не входят в тесты по умолчанию. Не запускать api-турниры
  без явного согласованного количества матчей/лимита затрат.
- Не придумывать актуальные ID моделей; проверять официальную документацию SDK при изменениях.
- Таймаут и output token cap одинаковы. SDK retries отключены, один запрос на ход.

## Проверка

Из корня проекта после установки зависимостей:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe game.py --mode demo --headless --matches 2 --max-turns 80
$env:SDL_VIDEODRIVER='dummy'
$env:SDL_AUDIODRIVER='dummy'
.\.venv\Scripts\python.exe game.py --mode demo --frames 30 --screenshot matches\smoke.png
```

Тестировать граничные значения JSON, фолы, королеву, сохранность ID, таймауты,
повторяемость и автоматическое завершение. API тестировать через mocks или
поддельный HTTP transport, без настоящих ключей. Архивные тесты запускать отдельно,
не добавлять legacy в коллекцию pytest новой версии.

В отчёте указывать реальные команды, код выхода, количество passed/failed,
проверенное окружение и что не проверялось. Изменения сохранять до запроса
одобрения на публикацию/деплой; локальная разработка уже разрешена пользователем.
